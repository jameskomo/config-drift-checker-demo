# notes-api — config-drift-checker demo

A deliberately small Spring Boot 3.5 / Java 21 service (create, list, get, archive notes; in-memory)
whose only purpose is to show **config-drift-checker** end to end: a repo that has a Claude Code setup —
`CLAUDE.md`, a conventions skill, a guard hook — and the eval suite that proves that setup still
works after every Claude Code release.

```
CLAUDE.md                          rules for coding agents (envelope, paging, archive-not-delete, run tests)
.claude-plugin/plugin.json         makes the repo a plugin so the setup can be loaded and tested
.cdc.yml                           pins (model id + Claude Code version), canary settings, thresholds, budget
agent-config/skills/…              the conventions skill
agent-config/hooks/…               PreToolUse guard (force-push, reset --hard, clean -f, rm -rf ..)
agent-config/evals/…               eval cases — generated by /config-drift-checker:setup, then curated; each says which rules it covers
.github/workflows/config-drift-checker.yml   pinned track on push/PR to the setup, or on demand (either track)
```

**Live results:** [interactive dashboard](https://jameskomo.github.io/config-drift-checker-demo/dashboard/) ·
[drift index](https://jameskomo.github.io/config-drift-checker-demo/) ·
[latest report](https://jameskomo.github.io/config-drift-checker-demo/report.html) ·
![agent-config coverage](https://raw.githubusercontent.com/jameskomo/config-drift-checker-demo/eval-results/docs/coverage.svg)

This repo runs the **pinned** track only — on push/PR to the setup, or manually (Actions →
config-drift-checker → Run workflow, where you can pick `canary` and tick `force`). There is no
schedule here on purpose: the product repo's own suite carries the scheduled canary
([drift index](https://jameskomo.github.io/config-drift-checker/drift/)), and this demo's `.cdc.yml`
caps spend at $3 a month whatever happens. A lapsed/low API key or a budget skip shows as a job-summary
notice, not a failing check — see the workflow file for why.

## Run the app
```bash
mvn -q -o test          # 2 tests
mvn spring-boot:run     # http://localhost:8080/api/notes
```

## Run the evals
```bash
claude --plugin-dir .                                   # interactive, setup loaded
node <config-drift-checker>/tools/eval-shim.mjs . --scaffold --track pinned   # or: claude plugin eval . --scaffold --allow-tools Read Glob Grep Edit Write Bash
node <config-drift-checker>/tools/config-coverage.mjs . --list                # which CLAUDE.md / skill / hook rules have a case
```
Results: `agent-config/evals/results/<timestamp>/{aggregate-result.json,report.html}`.

## Dashboards
Three views, all static, all from the `eval-results` branch that the Action pushes to after every run
(GitHub Pages serves that branch's `/docs`; the copy of `docs/` on `main` is dev source, not what's live):

- `docs/index.html` — the **drift index** generated by the Action: verdict, pinned baseline vs latest
  canary, budget spent this month, coverage, a ribbon of every case over every run, score per case
  across Claude Code versions, the run list.
- `docs/report.html` — the latest run's report: verdict, provenance stamp (model, Claude Code, track,
  cost), what moved, every run with grader reasons, tool calls and the response.
- `docs/dashboard/` — a small Vue 3 (CDN, no build) drill-down into one run, filterable by case/tag.
  The Action does not manage it; refresh its `data.json` by hand after a run you care about:
  ```bash
  node scripts/sync-dashboard-data.mjs   # rewrites docs/dashboard/data.json from the newest local run
  # then copy docs/dashboard/{index.html,data.json} onto the eval-results branch and push
  ```

See `docs/claude/README.md` for the walkthrough of how `setup` generated the cases.
