# notes-api — config-drift-checker demo

A deliberately small Spring Boot 3.5 / Java 21 service (create, list, get, archive notes; in-memory)
whose only purpose is to show **config-drift-checker** end to end: a repo that has a Claude Code setup —
`CLAUDE.md`, a conventions skill, a guard hook — and the eval suite that proves that setup still
works after every Claude Code release.

```
CLAUDE.md                          rules for coding agents (envelope, paging, archive-not-delete, run tests)
.claude-plugin/plugin.json         makes the repo a plugin so the setup can be loaded and tested
agent-config/skills/…              the conventions skill
agent-config/hooks/…               PreToolUse guard (force-push, reset --hard, clean -f, rm -rf ..)
agent-config/evals/…               eval cases — generated by /config-drift-checker:setup, then curated
.github/workflows/config-drift-checker.yml   runs the suite on push/PR to agent-config, CLAUDE.md, src — or on demand
```

**Live results:** [interactive dashboard](https://jameskomo.github.io/config-drift-checker-demo/dashboard/) ·
[trend across runs](https://jameskomo.github.io/config-drift-checker-demo/) ·
[latest static report](https://jameskomo.github.io/config-drift-checker-demo/report.html)

The workflow is deliberately **not** on a cron/release-watch schedule — it only runs when this repo's
own setup changes (push/PR) or when you trigger it manually (Actions → config-drift-checker → Run
workflow). That's a demo-repo choice to keep BYOK API spend predictable; a repo that wants "rerun
automatically on every new Claude Code release" restores the schedule trigger the product docs
describe. A lapsed/low API key shows as a job-summary warning, not a failing check — see the
workflow file for why.

## Run the app
```bash
mvn -q -o test          # 2 tests
mvn spring-boot:run     # http://localhost:8080/api/notes
```

## Run the evals
```bash
claude --plugin-dir .                                   # interactive, setup loaded
node <config-drift-checker>/tools/eval-shim.mjs . --scaffold  # or: claude plugin eval . --scaffold --allow-tools Read Glob Grep Edit Write Bash
```
Results: `agent-config/evals/results/<timestamp>/{aggregate-result.json,report.html}`.

## Dashboard
`docs/dashboard/index.html` is a small Vue 3 (CDN, no build step) app that renders whichever
`aggregate-result.json` it finds at `docs/dashboard/data.json` — filterable by case/tag, with a
"regressions only" and "failing runs only" toggle. It's a nicer, interactive drill-down into one
run's results, sitting alongside the two views CI already publishes automatically:
`docs/index.html` (a trend chart of score per case across every past run, generated by
`eval-dashboard.mjs`) and `docs/report.html` (the same drill-down as the Vue dashboard, statically
rendered, no JS required).

GitHub Pages actually serves from this repo's **`eval-results`** branch, `/docs` — an orphan branch
the CI Action pushes to after every run (`baseline.json`, `history/`, `docs/`). The copy of `docs/`
on `main` is dev source only, not what's live. `docs/dashboard/` was pushed to `eval-results`
directly since the Action doesn't manage it, and won't touch or delete it on future runs — but it
also won't refresh `data.json` for you the way it refreshes `report.html`. Until that's wired into
the Action's `store` step, refresh it by hand after a run you care about:
```bash
node scripts/sync-dashboard-data.mjs   # rewrites docs/dashboard/data.json from the newest local run
# then copy docs/dashboard/{index.html,data.json} onto the eval-results branch and push
```

See `docs/claude/README.md` for the walkthrough.
