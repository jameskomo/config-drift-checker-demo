# notes-api: the config-drift-checker demo

A deliberately small Spring Boot 3.5 / Java 21 service (create, list, get, archive notes; in-memory)
whose only purpose is to show **config-drift-checker** end to end. It is a repo with a real Claude
Code setup (`CLAUDE.md`, a conventions skill, a guard hook) and the eval suite that proves that
setup still works after every Claude Code release.

```
CLAUDE.md                          rules for coding agents (envelope, paging, archive-not-delete, run tests)
.claude-plugin/plugin.json         makes the repo a plugin so the setup can be loaded and tested
.cdc.yml                           pins (model id + Claude Code version), canary settings, thresholds, budget
agent-config/skills/…              the conventions skill
agent-config/hooks/…               PreToolUse guard (force-push, reset --hard, clean -f, rm -rf ..)
agent-config/evals/…               eval cases, generated by /config-drift-checker:setup and then curated; each says which rules it covers
.github/workflows/config-drift-checker.yml   pinned track on push/PR to the setup, or on demand (either track)
```

**Live results:** [interactive dashboard](https://jameskomo.github.io/config-drift-checker-demo/dashboard/) ·
[drift index](https://jameskomo.github.io/config-drift-checker-demo/) ·
[latest report](https://jameskomo.github.io/config-drift-checker-demo/report.html) ·
![agent-config coverage](https://raw.githubusercontent.com/jameskomo/config-drift-checker-demo/eval-results/docs/coverage.svg)

This repo runs the **pinned** track only, on push or PR to the setup, or manually (Actions, then
config-drift-checker, then Run workflow, where you can pick `canary` and tick `force`). There is no
schedule here on purpose: the product repo's own suite carries the scheduled canary
([drift index](https://jameskomo.github.io/config-drift-checker/drift/)), and this demo's `.cdc.yml`
caps spend at $3 a month whatever happens. A lapsed or low API key, or a budget skip, shows up as a
job-summary notice rather than a failing check; the workflow file explains why.

## Run the app
```bash
mvn -q -o test          # 2 tests
mvn spring-boot:run     # http://localhost:8080/api/notes
```

## Run the evals
```bash
claude --plugin-dir .                                   # interactive, setup loaded
node <config-drift-checker>/tools/eval-shim.mjs . --scaffold --track pinned   # or: claude plugin eval . --scaffold --allow-tools Read Glob Grep Edit Write Bash
node <config-drift-checker>/tools/config-coverage.mjs . --list                # which CLAUDE.md / skill / hook rules have a case
```
Results: `agent-config/evals/results/<timestamp>/{aggregate-result.json,report.html}`.

## Dashboards
Three views, all static, all served from the `eval-results` branch that the Action pushes to after
every run (GitHub Pages serves that branch's `/docs`; the copy of `docs/` on `main` is dev source,
not what's live):

- `docs/index.html` is the **drift index** the Action generates: verdict, pinned baseline vs latest
  canary, budget spent this month, coverage, a ribbon of every case over every run, score per case
  across Claude Code versions, and the run list.
- `docs/report.html` is the latest run's report: verdict, provenance stamp (model, Claude Code,
  track, cost), what moved, and every run with grader reasons, tool calls and the response.
- `docs/dashboard/` is a small Vue 3 interactive drill-down (CDN, no build): verdict, provenance
  stamp, diff against the baseline (score and turns/cost/time), filters, and three-state run cards
  with grader reasons, tool calls and responses. It reads the **live** `../latest.json` and
  `../baseline.json` the Action writes on every run, so it always shows the latest run. `data.json`
  in the folder is only a fallback for viewing the app somewhere those files don't exist
  (`node scripts/sync-dashboard-data.mjs` refreshes it from the newest local run).

See `docs/claude/README.md` for the walkthrough of how `setup` generated the cases.
